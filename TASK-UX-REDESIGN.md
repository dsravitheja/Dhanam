## Context you must load first

1. Read `CLAUDE.md` — it defines the single-file architecture, naming conventions (`v()`/`set()`/`el()` helpers, per-section ID prefixes, one `render*` entry point per feature), the service-worker cache-version rule, and the manual test checklist. **All of it stays binding.**
2. Read `UX-ANALYSIS.md` — the rationale for everything below.
3. Skim `index.html` end to end before editing; all CSS and JS are inline in that one file.

## Hard constraints

- **No build system, no dependencies, no framework.** Everything stays in `index.html` + `manifest.json` + `sw.js`. Inline SVG is fine; CDN scripts are not.
- **Preserve all calculation math.** This is a UX/structure task. Any refactor must keep every existing output numerically identical (spot-check against the checklist in CLAUDE.md, e.g. the 100%-tranche-at-month-0 ≡ plain EMI invariant).
- **Bump the `sw.js` cache version** with any shipped change (currently `apt-cost-v9`).
- Follow existing CSS custom properties and utility classes; do not invent parallel color systems.
- Verify by serving locally (`python3 -m http.server`) and walking the manual test checklist in CLAUDE.md, plus the new acceptance checks below.

**3c-a — Invalidate the chart cache when a host is cleared (R15)** — ✅ SHIPPED

**3c-b — Draw the step-up chart's baseline on one convention (R16)** — ✅ SHIPPED

- `updateStepupSIP()` builds `stepupSeries` from `calcStepupSIP` (month-by-month, ordinary annuity) and `flatSeries` from `calcSIP` (closed form, annuity-due). Those are the two sides of **B6**. A step-up SIP contributes exactly the same amount as a flat SIP for the whole of year 1 — the curves must coincide there. At 0% step-up the gold line sits ~1% below the grey one at *every* year, which reads as "stepping up 0% loses money".

**3c-c — Give the depreciation curve a real time axis (R17)** — ✅ SHIPPED

**6d-i — The comparison caveat (copy only; ships with R24, not after it)**

- **The problem, found by the owner running a real scenario on 2026-07-25.** The Buy-vs-SIP and prepay-vs-SIP comparisons put a **risky, pre-tax** number beside a **guaranteed, effectively tax-free** one and present the difference as if it were real. **6e-i — What the feedback mechanism may and may not be (owner question, 2026-08-07)**

The owner asked whether this should be a Google Form or an in-app feedback tab. **The privacy claim decides it, not preference**, so the reasoning is recorded here rather than left to whoever builds it.

**Disqualified outright — an embedded form or feedback widget.** A Google Form `<iframe>`, Formspree, Canny, Usersnap, Hotjar or any drop-in widget fires an off-origin request **on page load**, whether or not anyone ever submits. That contradicts "nothing is ever sent anywhere" on every single visit, and it re-creates precisely the request **R5 spent Phase 4 removing** — three font families were self-hosted specifically so a stranger opening devtools sees zero off-origin traffic. Do not undo that for a feature nobody asked for. *(A form **linked** out to, rather than embedded, is not disqualified — the user consciously leaves the app — it's just weak; see below.)*

**Weak, though allowed — a linked-out Google Form.** Costs nothing to stand up and yields a tidy spreadsheet, but it loses the thing that makes beta feedback worth having: **context**. The valuable report is "this number looked wrong, on this screen, with these inputs"; a form in a separate tab asks the user to reconstruct that from memory, and most won't. Acceptable as a fallback link, not as the primary route.

**Build this instead — a local composer that sends nothing.** A feedback panel that takes the user's message, appends a small **technical** context block gathered client-side — active hub/section, build stamp (R45), viewport width, user-agent, and whether `localStorage` is readable/writable (`storageUnreadable`/`storageFailed`, which are otherwise invisible and are the app's hardest-to-diagnose failure class) — then hands off through **two** buttons: `mailto:` with the body prefilled, and **Copy to clipboard** (for WhatsApp, and because `mailto:` is unreliable on machines with no configured mail client).

Why this shape, specifically for this app:

- **The app still makes zero network requests.** The user's mail client sends; the app composes. The privacy claim survives verbatim *and* stays devtools-verifiable, which is the property 6b exists to give a stranger.
- **It is a stronger privacy stance than a form, not a weaker one** — the user reads the exact text before anything leaves, and can delete any of it.
- **It keeps the context a form loses**, without a server.
- **It works offline**, like the rest of the PWA: compose now, send when reconnected.

⚠️ **The context block is technical only.** No balances, no salary, no `dhanam.v1` contents, no calculator inputs — and no "attach my data to help debug" toggle, however convenient it looks during a beta. That toggle is the exact creep the **Out of scope** section warns about, and it would forfeit the promise more cheaply than a backend would.

**Sequencing (owner-agreed).** For the close-circle beta, **do not build the composer first.** With 5–10 people the channel already exists (WhatsApp, and a call), and **6f's argument applies directly: written feedback structurally invites the low-signal kind** — opinions, feature requests, compliments — which 6f says to discount in favour of watching someone attempt a real task. So: **beta = R45's build stamp + a plain contact link + the 6f protocol.** Build the composer **before the public release**, when the people using it are no longer people you can ring up.

### Phase 7 — Post-tax honesty (D12) — ❌ NOT STARTED (**R31**, **R32**; needs B10)

> **Why this exists.** On 2026-07-26 the owner ran a real scenario through the app — delay a house purchase two years, invest the would-be EMI as an SIP — and found the numbers flattered the SIP. Two separate problems fell out, and **they need different treatments**:

> ⚠️ **The distinction matters more than either fix.** A disclaimer is the right answer when the app can't know something — the user's redemption date, or what tax law says in 2046. It is *not* an answer when the app presents two incomparable numbers as comparable, because most people read the number and not the note. Apply the test: **if the user reads only the hero figure, are they misled, or merely imprecise?** Misled ⇒ change the figure or the framing. Imprecise ⇒ a dated, plainly-worded disclaimer is honest and sufficient. **7a — Post-tax as a secondary figure in Grow (R31)**

- **The hero stays pre-tax; post-tax goes beside or beneath it.** Do not create a second hero, and do not double every number on screen. Adding a twin to every headline figure would quietly undo part of that.

**7b — Tax-aware modeling (R32) — assess before building**

- The honest version of this is genuinely hard, and **the first task is to decide whether it's worth doing at all.** Committed scope is the assessment; the implementation is a follow-on decision.
- What "correct" would require: **each SIP installment carries its own holding-period clock**, so a redemption splits into long-term and short-term buckets by installment date; the annual LTCG exemption applies per financial year; and the loan side of any comparison has its own untaxed benefits (Section 24 interest deduction, 80C principal, old regime only) that the app currently ignores in the opposite direction.
- ⚠️ **`calcSIP` structurally cannot express this.** It's a closed-form annuity with no per-installment representation. Only a month-by-month simulation can — that's `calcStepupSIP`'s shape. Any tax layer either builds on the simulator or is an approximation that should be labelled as one. **See B6:** the two functions already disagree by ~1%, and a tax layer built on one of them inherits that disagreement.
- ⚠️ **The false-precision risk is the real argument against building it.** Tax treatment on equity changed in 2018, 2023 and 2024. A post-tax figure projected 20 years out asserts a redemption event that may never happen, under rules that certainly will change. **A number that is precisely wrong is worse than a range that is roughly right** — and worse than an honest "we don't model this."
- ⚠️ **Do not let this become investment advice.** Modeling tax to help someone understand a number is a calculator. Ranking instruments by after-tax outcome edges toward recommendation, which is the line 6b's disclaimer is written to stay behind. A lawyer's read applies here too.
- **A cheaper alternative worth pricing first:** state the assumption instead of modeling it — "assumes redemption at year N, taxed at the current LTCG rate; your actual outcome depends on when you sell." That may capture most of the honesty benefit at a fraction of the cost and risk. Decide between these two before writing any code.
- *Acceptance (of the assessment):* a written recommendation — build, approximate, or state-and-don't-model — with the reasoning recorded here so it isn't relitigated; if "build", `calc.js` gains pure, tested functions and `node tests.js` covers the LTCG/STCG split, the exemption boundary, and the zero-gain edge case.

#### Corrections the app must make (do not port these from the workbook)

Five of these are real; the first two change the answer materially.

1. **The residual buyout is credited nothing (R40).** The workbook adds the balloon buyout to cash outflow and stops — as if the car evaporates at term end. It doesn't; you own it. `calcCarDepreciation(2000000, 4)` returns **₹9.83L against a ₹2.00L buyout on a ₹20L car — a ₹7.83L credit the model drops**, and because it scales with on-road price, it doesn't just inflate every total equally, it **reorders the ranking** in favour of cheaper cars. This is the single biggest reason the app version beats the spreadsheet.
   - Show it as its own line ("estimated value of the car you now own"), never silently netted into net cost. `calcCarDepreciation` is an IRDAI *insurance* depreciation schedule, not a resale-price predictor, and it is a single ICE-shaped curve — EV residuals behave differently (battery health, faster model turnover). Both caveats go in the section's caveat list.
   - B12 decides whether the rank is computed pre- or post-credit.
2. **The perquisite is not a flat ₹5,000 (already fixed in `calc.js`, must not be re-broken).** The workbook hardcodes ₹5,000/month for every car. `calcPerquisite(bigEngine, hasDriver)` has held the Income-tax Rules, 2026 table since Phase 8b: **₹5,000 for ≤1.6L *or electric*, ₹7,000 above 1.6L, +₹3,000 for a chauffeur.** Over a 4-year term at a 31.2% marginal rate, the workbook overstates tax saved on a >1.6-litre ICE car by **₹29,952** — and an EV of any size stays in the ₹5,000 bracket, so this is a **structural EV advantage the workbook erases entirely.** `calcLeaseNetCost` must take the perquisite from `calcPerquisite`, and an `ev` row must pass `bigEngine = false` regardless of motor size.
3. **`calcInsuranceTotal` divides by the depreciation rate.** The workbook's closed-form geometric series is `price × rate × (1 − (1−dep)^years) / dep`, which is `0/0` at `dep = 0` — a value a user can type. Guard it: `dep === 0 ⇒ price × rate × years`. Verified equal to a year-by-year loop at `dep = 15%` (₹191,197.50 both ways) and at `dep = 0` (₹240,000 both ways).
4. **Rank 1 is gold, not green.** The workbook green-highlights the cheapest row. In this app green means *a real, positive financial delta* (palette rule 3); "this is the selected/best option" is emphasis, which is **gold** (palette rule 2). Do not introduce a fourth meaning for green.
5. **Drop the workbook's "EV annual mileage multiplier."** It models a rebound effect (people drive EVs more because running cost feels negligible) by scaling EV annual km. The workbook is honest that this makes its own ₹/km column incomparable across types — the two figures end up with different denominators. One fewer knob, and one fewer way to read the headline number wrong. Note the omission in the caveat list rather than silently dropping it.

**Two traps this codebase has already been bitten by, which this section walks straight back into:**

- **The blank-row guard must read raw input state (workbook §8).** That bug — blank rows falling through into the EV branch and ranking as "cheapest" — has an exact JS analogue: a `price || 0` or a truthy check treating a *typed* `0` as an unfilled row, or an unfilled row as a legitimate ₹0 car. This app has shipped that bug before: **R16's `su-stepup` `|| 10` fallback** treated an explicit `0` the same as blank. A row participates only if **both** on-road price **and** mileage/efficiency are `> 0`, checked against the field's own raw value.
- **`renderCCRows()` must not run on every keystroke.** The car table is the same shape as `disbTranches` — an array of objects rendered into editable rows — and it inherits the same hazard. Rewriting the rows' `innerHTML` on `oninput` drops keyboard focus mid-typing. **This was D6/Phase 0, a real shipped bug in `section-disb`.** Follow the existing rule exactly: `renderCCRows()` on add/remove/reset only; `renderCarCompare()` recomputes and rewrites *results* from current state without touching the input rows.

**9a — `calc.js`: balloon EMI and four new pure functions (R38)**

No DOM, no UI, `node tests.js` coverage — this lands independently and first.

- **`calcEMI(P, annualRate, years, fv = 0)`** — add a fourth optional argument, the future value still owed at term end. A company lease is not an amortizing loan: the EMI only has to amortize `P − PV(residual)`.
  ```
  r = annualRate/12/100 ;  n = years*12
  fv === 0 → unchanged
  r === 0  → (P − fv) / n
  else     → r * (P*(1+r)^n − fv) / ((1+r)^n − 1)
  ```
  **The default matters more than the formula.** Every existing caller (`loanAtYear`, `simulateLoan`, `renderLoans`, `renderAdvLoan`, `renderCarLoan`, `renderLoanDisb`, `renderWorthProjection`) passes three arguments and must be bit-identical afterwards. Verified: at `fv = 0` the new expression returns `50725.166869` where the current one returns `50725.166869`, and all 47 existing tests pass unchanged. **Add a test that pins this identity**, so a later "simplification" of the formula can't drift the whole app's loan math by a rupee.
  - Correctness oracle for the `fv` path: amortize month by month at the returned payment; the balance after `n` months must equal `fv` exactly. Verified — ₹2,000,000 at 10% over 4 years with a ₹200,000 residual gives ₹47,319.32/month and a terminal balance of ₹200,000.0000.
- **`calcRunningCost(type, spec, a)` → `{ annual, perKm }`** — return both from one call. `perKm` is what `calcBreakevenKm` needs, and the workbook's §6 explicitly warns that deriving it from the annualized total is what breaks when an assumption changes. One function, one source of truth.
  ```
  ICE: cityKm/kmpl*petrol + hwyKm/(kmpl*iceHwyMult)*petrol
  EV : cityKm*(kWhPer100/100)*homeRate + hwyKm*(kWhPer100*evHwyMult/100)*publicRate
  perKm = annual / (cityKm + hwyKm)
  ```
  Guard `kmpl <= 0` and `cityKm + hwyKm === 0` — both are typeable and both produce `Infinity`/`NaN` today.
- **`calcInsuranceTotal(price, rate1, depRate, years)`** — geometric series, with the `depRate === 0` guard from correction 3 above.
- **`calcLeaseNetCost({...}) → { emi, months, residual, runningTotal, maintTotal, insTotal, taxSaved, rawOutflow, netCost, resaleValue, netCostAfterResale, costPerKm }`** — the engine.
  ```
  taxSaved   = marginalRate * (emi − calcPerquisite(bigEngine, hasDriver)) * months
  rawOutflow = emi*months + residual + runningTotal + maintTotal + insTotal
  netCost    = rawOutflow − taxSaved
  netCostAfterResale = netCost − calcCarDepreciation(price, years)     // R40
  ```
  `taxSaved` stays **signed**. If the EMI is below the perquisite you are genuinely taxed on more than you carve out, and a `Math.max(0, …)` would hide a real negative. The workbook's §8 bug was blank rows exploiting exactly this — the fix is the row guard, not clamping a legitimate number.
  - `marginalRate` is a plain argument. v1's caller reads it from a slab dropdown (30% + 4% cess = 31.2% default). **Flagged, not scoped:** the more correct source is a delta from the app's own `calcIncomeTax` — `tax(taxable) − tax(taxable − (emi − perq)*12)` — which would pick up the Section 87A marginal relief R34 just added and bridge this section to the salary the user already entered in the lease panel above. Keeping `marginalRate` as an argument means that upgrade is a caller change only, with no signature churn.
- **`calcBreakevenKm(evFixed, evPerKm, iceFixed, icePerKm, years)`** — `(evFixed − iceFixed) / (years * (icePerKm − evPerKm))`, where `fixed` is every km-independent component (EMI × months + residual + maintenance + insurance − tax saved).
  - **Three outcomes, three distinct returns — the workbook specifies none of them.** Denominator `<= 0` (the EV costs more per km): return `null`, meaning *never breaks even*, and render that as a sentence, not as `Infinity`. Result `<= 0`: the EV is already cheaper at any mileage — render "already cheaper today", never a negative km figure. Otherwise the number.
- *Acceptance:* `node tests.js` green with the existing 47 plus new cases for — `fv = 0` identity against the pre-change `calcEMI`; the balloon amortization oracle; zero-rate balloon `(P−fv)/n`; `calcInsuranceTotal` closed-form vs. a year-by-year loop at `dep = 15%` and the `dep = 0` guard; `calcRunningCost` satisfying `perKm × totalKm === annual` and surviving a zero-mileage row; `calcLeaseNetCost` satisfying `netCost === rawOutflow − taxSaved`; a **pin that `calcLeaseNetCost` sources its perquisite from `calcPerquisite`** (a big-engine ICE row must differ from an EV row by exactly `marginalRate × 2000 × months`, ₹29,952 at the defaults) so correction 2 can't be un-fixed by a future edit; all three `calcBreakevenKm` branches.

## Out of scope

Backend/accounts/sync, new calculator types beyond Worth, frameworks or build tooling, analytics of any kind, changing any financial formula.

**On accounts specifically:** user accounts are a noted future direction and are understood to require a real backend (`UX-ANALYSIS.md` §2.5). They are out of scope here and must not be half-built — no "optional cloud backup", no telemetry as a stepping stone, nothing that forfeits the "never sent anywhere" promise without actually delivering accounts. Nothing in Phase 2 has to be undone to add them later: the tier-1/tier-2 split is exactly the store-vs-compute boundary a server would use, and the Option C JSON schema is the natural sync payload.

**On Firebase specifically (B9, raised 2026-07-25).** Still out of scope, but the question is now live enough to write down the conditions rather than re-derive them under pressure later. This is not legal advice and a lawyer's read is needed before any of it ships.

- **The privacy promise is a one-way ratchet.** "Nothing is ever sent anywhere" can be tightened silently; it cannot be loosened silently. The day any user data reaches a server, that copy has to change **everywhere it appears** — landing page, About page (6b), Worth hub — *before* the feature ships, not after. Shipping the backend first and updating the copy later is the one failure mode that would do real damage to the thing the app is trying to be.
- **Don't adopt a backend for sync convenience.** Cross-device is already solved, imperfectly but honestly, by the Option C JSON backup. Adopt a server only when a feature genuinely cannot exist without one — and name that feature first. "It would be nice to have accounts" is not a feature.
- **If it happens anyway, the shape that preserves the promise** is: opt-in (the app stays fully functional and local-only for anyone who declines), storing the same tier-1 JSON payload the backup already produces, **encrypted client-side before upload** so the server holds a blob it cannot read. That keeps balances unreadable to Firebase, to Google, and to a future compromised deploy — and it's the only version where the marketing claim survives roughly intact.
- **Firebase-specific hazards worth knowing before choosing it.** In a client-side app with no server of your own, **Firestore security rules are the entire security model** — a misconfigured rule is the single most common way this stack leaks data, and there is nothing behind it. Pick an Indian region (`asia-south1`) deliberately rather than accepting the default. And note that "no analytics" becomes harder to hold: several Firebase products enable telemetry by default, which would quietly contradict the stance taken in 6e.
- **Regulatory weight goes up, not down.** Net worth, salary and loan balances are personal financial data; the moment it's held on a server, obligations under India's DPDP Act (2023) — consent, purpose limitation, breach notification, deletion on request — attach to *you* in a way they simply don't for `localStorage`. "Erase my data" stops being a one-line `localStorage.clear()` and becomes a promise you have to be able to keep on someone else's infrastructure.
- **Sequencing:** do not start this before Phase 6 lands. Phase 6 is what makes the app trustworthy to a stranger; a backend added first would mean asking strangers to trust a server before the app has explained what it does with anything.
